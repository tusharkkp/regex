Section 2

Regex Design & Pattern Analysis

Each field uses carefully designed regular expressions with anchors, quantifiers, character classes, groups, and lookaheads.

👤
Username Validation
^(?=.{3,20}$)[a-zA-Z][a-zA-Z0-9_]*$

^ $ - Anchors ensuring full-string match

(?=.{3,20}$) - Positive lookahead: enforces 3-20 character length

[a-zA-Z] - Character class: first char must be a letter

[a-zA-Z0-9_]* - Quantifier *: zero or more word characters

📧
Email Validation
^(?=.{5,254}$)[a-zA-Z0-9._%+-]+@[a-zA-Z0-9.-]+\.[a-z]{2,}$

(?=.{5,254}$) - Lookahead: RFC-compliant length limit

[a-zA-Z0-9._%+-]+ - Local part with + quantifier (one or more)

@ - Literal separator between local and domain parts

[a-zA-Z0-9.-]+ - Domain: letters, digits, dots, hyphens

\.[a-z]{2,} - TLD: dot + minimum 2 lowercase letters via {2,}

📄
File Name Validation
^(?=.{1,100}$)[a-zA-Z0-9][a-zA-Z0-9_-]*\.(jpg|jpeg|png|gif|pdf|docx?|txt)$

(?=.{1,100}$) - Lookahead: max 100 chars total

[a-zA-Z0-9] - Must start with alphanumeric character

[a-zA-Z0-9_-]* - Body allows underscores and hyphens

(jpg|jpeg|png|gif|pdf|docx?|txt) - Alternation group: allowed extensions

docx? - ? quantifier makes 'x' optional (matches doc and docx)

🛡
File Type Safety (Negative Lookahead)
^(?!.*\.(exe|bat|sh|cmd|msi|dll|com|scr|vbs|ps1)$).+\.[a-zA-Z]{2,5}$

(?!.*\.(exe|bat|...)$) - Negative lookahead: blocks dangerous executable extensions

This is a key TOC concept - lookaheads extend regex power beyond basic regular expressions

.+ - At least one char for filename body

[a-zA-Z]{2,5} - Extension must be 2-5 alphabetic characters

📊
File Size Validation
^([1-9]\d{0,5}|0)(\.\d{1,2})?\s?(KB|MB|GB)$

([1-9]\d{0,5}|0) - Alternation group: number without leading zeros, or literal 0

(\.\d{1,2})? - Optional group with ?: decimal up to 2 places

\s? - Optional whitespace between number and unit

(KB|MB|GB) - Capture group with alternation: valid size units

📝
Description Validation
^(?=.{10,500}$)(?=.*[a-zA-Z]{3,})[a-zA-Z0-9\s.,;:!?'"-]+$

(?=.{10,500}$) - Lookahead #1: enforces length range

(?=.*[a-zA-Z]{3,}) - Lookahead #2: must contain a real word (3+ letters)

Multiple lookaheads demonstrate advanced regex composition

[a-zA-Z0-9\s.,;:!?'"-]+ - Whitelist of safe characters

Section 3

Formal Language Theory

Each regex defines a formal language over an alphabet Sigma. We prove each is a regular language recognizable by a finite automaton.

👤
Username - Formal Definition
Alphabet (Sigma)
Sigma = { a-z, A-Z, 0-9, _ }
Language Definition
L = { w in Sigma* | 3 <= |w| <= 20, w1 in [a-zA-Z], wi in Sigma for i > 1 }
Regularity Justification
This language is regular because it can be described by a regular expression and recognized by a DFA with a finite number of states tracking position and length. The length constraint (3-20) requires at most 21 states, and character class checks are handled by transition functions - all finite. By Kleene's theorem, any language described by a regex is regular.
📧
Email - Formal Definition
Alphabet (Sigma)
Sigma = { a-z, A-Z, 0-9, ., _, %, +, -, @ }
Language Definition
L = { w in Sigma* | w = u@v.t, u in [a-zA-Z0-9._%+-]+, v in [a-zA-Z0-9.-]+, t in [a-z]{2,} }
Regularity Justification
The email pattern is a concatenation of regular sub-patterns separated by literals (@ and .). Since regular languages are closed under concatenation (proven via NFA construction), the resulting language is regular. The TLD constraint {2,} is expressible with finite repetition in a DFA.
📄
File Name - Formal Definition
Alphabet (Sigma)
Sigma = { a-z, A-Z, 0-9, _, -, . }
Language Definition
L = { w in Sigma* | w = name.ext, |w| <= 100, name in [a-zA-Z0-9][a-zA-Z0-9_-]*, ext in {jpg, jpeg, png, gif, pdf, doc, docx, txt} }
Regularity Justification
The filename language is the concatenation of a name pattern (regular), a literal dot, and a finite union of extension strings. Finite unions of regular languages are regular (closure under union). The length bound can be tracked by a DFA with bounded states.
🛡
File Type - Formal Definition
Alphabet (Sigma)
Sigma = { a-z, A-Z, 0-9, _, -, . }
Language Definition
L = { w in Sigma* | w = name.ext, ext in [a-zA-Z]{2,5}, ext not in {exe, bat, sh, cmd, msi, dll, com, scr, vbs, ps1} }
Regularity Justification
The negative lookahead implements set difference: L(safe) = L(all_extensions) - L(blocked). Since regular languages are closed under complement and intersection (by DFA product construction), the result is regular. The blocked set is finite and thus trivially regular.
📊
File Size - Formal Definition
Alphabet (Sigma)
Sigma = { 0-9, ., K, M, G, B, space }
Language Definition
L = { w in Sigma* | w = n[.d][ ]u, n in {0} U [1-9][0-9]{0,5}, d in [0-9]{1,2}, u in {KB, MB, GB} }
Regularity Justification
This is a concatenation of a numeric part (finite digit sequences are regular), an optional decimal, optional space, and a finite set of units. All components are regular, and their concatenation is regular by closure properties.
📝
Description - Formal Definition
Alphabet (Sigma)
Sigma = { a-z, A-Z, 0-9, space, ., ,, ;, :, !, ?, ', ", - }
Language Definition
L = { w in Sigma* | 10 <= |w| <= 500, exists substring u in w such that u in [a-zA-Z]{3,} }
Regularity Justification
Length bounds create finite state tracking (regular). The "contains a word" constraint is equivalent to Sigma*.[a-zA-Z]{3,}.Sigma* - a concatenation of regular languages. The intersection of these constraints remains regular (closure under intersection).

Section 6

Code Architecture

Modular JavaScript validation with documented regex patterns and real-time feedback.

Architecture Overview

The project follows a modular architecture with clear separation of concerns:

- styles.css - Design system with CSS custom properties (tokens)

- script.js - Validation engine with formally documented regex

- index.html - Structure, academic sections, and interactive form

Each validation function (validateUsername(), validateEmail(), etc.) is self-contained with specific error messages for different failure modes.

Key Design Decisions

1. Lookaheads for Length Constraints - Instead of checking .length separately, we embed (?=.{min,max}$) directly in the regex to keep validation purely regex-driven, aligning with TOC principles.

2. Negative Lookahead for Security - The file type validator uses (?!.*\.(exe|bat|...)$) to implement set complement, demonstrating that regular languages are closed under complement.

3. Real-time Feedback - The oninput event triggers validation on every keystroke, providing immediate visual feedback via CSS class toggling (.valid / .invalid).

4. Contextual Error Messages - Each validator checks multiple failure conditions (too short, wrong start char, invalid chars) to provide helpful, specific feedback rather than generic "invalid" messages.
